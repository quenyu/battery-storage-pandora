# Исследование: учёт, хранение и прослеживаемость АКБ Pandora

Статус: проект API для обсуждения, 30.09.2026. По сообщению пользователя руководитель согласовал текстовые адреса вместо таблиц мест; остальные неподтверждённые правила отмечены отдельно. Этот пакет не заменяет действующий демонстрационный API.

## Источники и границы знания

Основной источник — описание задачи пользователем в этом чате. Наблюдения репозитория: `README.md`, `assets.go`, `internal/api/{server,batteries}.go`, `docs/design/battery-storage-pandora/{codex-task,spec,architecture,schema}.md/sql`, документы `battery-storage-mock`. Здесь уже реализована локальная демонстрация: UUID, встроенное текущее состояние, журнал операций, повтор запросов, Swagger UI. Контракт встроен из `battery-storage-pandora/openapi.yaml`.

В старых документах есть принятые для демонстрации решения: максимум одна АКБ в ячейке, один активный credential сотрудника, возврат другим сотрудником, отсутствие входа, операция потери. Они не являются подтверждением процессов предприятия. В текущем интервью пользователь подтвердил одну АКБ на ячейку и возврат только текущим держателем; несколько credential остаются требованием. Реальный RETURN поэтому отличается от демонстрации. Новый пакет сохранён отдельно в `battery-storage-discovery`. Код, действующий OpenAPI и миграции не менялись. Git-метаданные в рабочей папке отсутствуют; сравнение с веткой невозможно.

Последующее уточнение пользователя: руководитель ответил «Шкафы полки и ячейки не нужно в отдельную таблицу выносить» и «Достаточно просто текстом в battery_operation все это хранить». Это решение заменяет первоначальное требование нормализовать места. Приложенная ER-картинка показывает прежние семь таблиц. Актуальная модель — четыре предметные таблицы и техническая таблица повторов; source/destination_location TEXT в журнале, current_location TEXT в projection. Фото не является источником новых команд или полномочий.

Публичные сведения о компании не доказывают устройство её складов, используемые АКБ, наличие AD/LDAP/1С, электронных замков или датчиков. Эти вопросы требуют ответа наставника либо наблюдения рабочего процесса.

## Назначение и словарь

Система ведёт индивидуальный учёт АКБ и фиксирует каждую подтверждённую операцию. Для одной АКБ можно получить её текущее место или держателя и последовательность размещений, выдач, возвратов и перемещений. Ценность — возможность объяснить, кто, когда и откуда забрал конкретную АКБ, куда она вернулась и через какое известное устройство была оформлена операция.

АКБ — отдельный физический предмет учёта; её химия, модель и производственная функция неизвестны. ШК — упомянутый наставником идентификатор; физический способ чтения не установлен. Credential — значение предъявляемого идентификатора сотрудника, отделённое от employee.id и табельного номера. Custody — учётный держатель АКБ, а не доказательство юридической ответственности. Операция — подтверждённое изменение учёта; HTTP-запрос может повторяться без новой операции. Ячейка — место внутри полки внутри шкафа; `1.1.1` — пример текстового адреса, который после уточнения руководителя хранится целиком; итоговый формат ещё не подтверждён.

Сканирование доказывает ввод идентификатора в клиент, но само по себе не доказывает физическое изъятие, возвращение или присутствие человека. У MVP нет подтверждённого оборудования, которое измеряет эти факты.

## Данные и процессы

Master data: сотрудники и их credentials; реестр АКБ — устойчивые учётные объекты. Transactional: current status/location/holder/version и results идемпотентных команд. History: immutable battery_operations с текстовыми source/destination и участниками. Administrative audit сотрудников/credential имеет иной смысл; audit_log пока future extension. Шкафы/полки/ячейки и devices отдельными справочниками в текущем варианте не ведутся.

Основной процесс: подготовка сотрудников/карт → регистрация и первое STORE → TAKE → RETURN → MOVE. Чтения сопровождают учёт. Смена карты не меняет человека. Текстовые адреса сохраняются в истории, однако отсутствие справочника не позволяет отключать места или подтверждать их физическое существование. Условия хранения/измерения — неподтверждённые отдельные процессы.

## Что уже известно

- Общий Go REST API для Web и ТСД; PostgreSQL; pgx и явный SQL; OpenAPI и Swagger UI.
- Требуется индивидуальная прослеживаемость и быстрый запрос текущего состояния.
- Физически cabinet → shelf → cell; по последующему решению руководителя эта иерархия не представлена отдельными таблицами. Места в операциях — текст.
- Employee ID, табельный номер и credential различаются. Значения идентификаторов — строки с сохранением ведущих нулей.
- Минимальные операции: STORE, TAKE, RETURN, MOVE. MOVE сохраняет оба конца.
- История не переписывается обычным UPDATE; новое состояние и операция атомарны.
- Нужно исключить двойную выдачу, двойное применение повторного запроса и разрушение истории при замене карты / изменении текущего адреса.
- Полный production backend сейчас не требуется. Реализация после проработки и согласования.
- Уточнение пользователя в интервью: в одной ячейке строго одна АКБ; вернуть может только тот сотрудник, который её взял.

## Use cases

Общие условия для команд: доверенный аутентифицированный API-клиент, серверная проверка прав, UUID Idempotency-Key, одна АКБ на запрос. Это предлагаемый технический контракт. Credential определяет участника, но не заменяет вход. Политика прав пока не подтверждена. Ошибка до COMMIT не оставляет частичного движения. Сохранённый повтор возвращает исходный результат, а не новое состояние.

### UC01. Получение / регистрация сотрудника по credential

Вход: `POST /credential-resolutions` с credential_value; при регистрации — `POST /employees` с именем и необязательным personnel_number, затем `POST /employees/{id}/credentials`. Проверки: право чтения/ведения справочника, точное строковое значение, active credential и active employee. Неизвестный скан не создаёт человека автоматически. Изменение: lookup ничего не пишет; регистрация создаёт employee, назначение credential — отдельную строку. Событие: движения АКБ нет, административное изменение кандидат для audit. Результат: employee.id и credential.id без преобразования в число. Ошибки: 400 неверный JSON; 404 CREDENTIAL_NOT_FOUND; 403 EMPLOYEE_INACTIVE/доступ; 409 ACTIVE_CREDENTIAL_EXISTS или политика повторного использования.

### UC02. Регистрация и размещение новой АКБ

Вход: POST /batteries, inventory_code, actor_credential_value, destination_location TEXT, optional serial_number. Проверки: actor/права, уникальность кода, непустой канонический адрес без крайних пробелов, отсутствие учтённой АКБ на том же адресе. Физическое существование места не проверяется FK. Изменение: STORED(location), version1, STORE и result key одной транзакцией. Событие: source NULL, destination текстом, actor. Результат: 201 CommandResult. Ошибки: 409 INVENTORY_CODE_EXISTS/LOCATION_OCCUPIED; 422 адрес; 403 права; 404 actor credential. Если нужна отдельная регистрация до размещения — Q29 и отдельный REGISTER/unplaced после согласования.

### UC03. TAKE

Вход: ID АКБ, actor credential; optional expected_version/observed_source_location. Проверки: STORED, права/active actor, ожидания совпадают с server current под FOR UPDATE. Изменение: ISSUED, location NULL, holder actor, version+1. Событие: TAKE с source_location из сервера и destination holder. Результат: 201. Ошибки: 409 BATTERY_ALREADY_ISSUED/INVALID_BATTERY_STATE/STATE_VERSION_MISMATCH/SOURCE_MISMATCH, 403, 404. Клиент не задаёт authoritative source.

### UC04. RETURN

Вход: battery ID, actor credential, destination_location, optional expected_version. Проверки: ISSUED; actor=current holder по employee.id; права и текстовый адрес. Изменение: STORED(destination), holder NULL, version+1. Событие: RETURN, source holder и actor совпадают по подтверждённому правилу. Результат: 201. Ошибки: 403 RETURN_NOT_ALLOWED для другого сотрудника; 409 INVALID_BATTERY_STATE/LOCATION_OCCUPIED/STATE_VERSION_MISMATCH; 422 адрес; 404 battery/credential. Смена карты того же сотрудника возврату не мешает.

### UC05. MOVE

Вход: battery ID, actor credential, destination_location; optional expected_version/observed_source_location. Проверки: STORED, server source, destination отличается, адрес не занят по учёту. Изменение: STORED с новым current_location, version+1. Событие: MOVE с обоими текстовыми концами. Результат: 201. Ошибки: 409 SOURCE_MISMATCH/SAME_LOCATION/INVALID_BATTERY_STATE/STATE_VERSION_MISMATCH/LOCATION_OCCUPIED; 403/404/422. UNIQUE занятого текста защищает конкуренцию; ошибка откатывает новый event/current и сохраняет исходный адрес.

### UC06. Получение текущего состояния

Вход: GET /batteries/{id} или exact inventory_code в списке. Проверки: право чтения и ID. Изменение/событие: нет. Результат: 200 status/version/current_location либо holder из одной projection-строки, без replay. Ошибки: 404 BATTERY_NOT_FOUND, 401/403.

### UC07. История АКБ

Вход: `GET /batteries/{id}/operations`, курсор. Проверки: существование АКБ, право чтения, валидность курсора. Изменение/событие: нет. Результат: 200, последовательность по battery_version с участниками, концами и server occurred_at. Ошибки: 404; 400 INVALID_CURSOR; 401/403. Пустая история только для отсутствующих движений не подменяет 404.

### UC08. Получение содержимого текстового места

Вход: GET /batteries?location=1.1.1. Проверки: право чтения, валидный query. Изменение/событие: нет. Результат: 200 список 0/1 АКБ по exact current_location. Пустой список не доказывает физическое существование пустой ячейки; справочника и 404 CELL_NOT_FOUND нет. Ошибки: 400 syntax/cursor, 422 filter, 401/403.

### UC09. Выданные АКБ сотрудника

Вход: `GET /employees/{id}/batteries`. Проверки: сотрудник существует и доступен читателю; историю/долги отключённого сотрудника не прятать. Изменение/событие: нет. Результат: 200, batteries WHERE holder_employee_id=id AND status=ISSUED. Ошибки: 404 EMPLOYEE_NOT_FOUND; 401/403. Смена credential на результат не влияет.

### UC10. Повтор после timeout

Вход: тот же клиент, ключ, путь и нормализованное тело. Проверки: текущий доступ клиента, затем request_hash. Изменение: если команда уже зафиксирована, нет; если её транзакция откатилась — выполнить как новую с тем же ключом. Событие: максимум одно успешное движение для ключа. Результат: первоначальные HTTP status/body; GET нужен для свежего состояния. Ошибки: 409 IDEMPOTENCY_KEY_REUSED для другого содержимого; 503, если ожидание занятого ключа превысило технический timeout. Новый ключ после неопределённого ответа не генерировать.

### UC11. Два конкурентных TAKE

Вход: два разных ключа / сотрудника для одной STORED АКБ. Проверки: оба блокируют строку battery; второй ждёт первый COMMIT, затем читает ISSUED. Изменение: единственный переход и один holder. Событие: одна TAKE. Результат: один 201, второй 409 BATTERY_ALREADY_ISSUED. Если первый ROLLBACK — второму разрешён успех. Для одного общего ключа действует UC10, а не второй бизнес-переход.

## Возможные интеграции

Источник сотрудников, система аутентификации, считыватель ТСД, маркировка мест/АКБ, замки шкафа, датчики среды, измерительное оборудование, отчётность. Каждая требует отдельного подтверждения, протокола и владельца данных. В MVP нет ни одной утверждённой внешней интеграции. Полноценный offline и управление физическими замками меняют границу атомарности и требуют отдельного этапа.

## Продолжение

Приняты из текущего диалога: одна АКБ на место; RETURN только взявшим; подробная реализация ТСД вне этапа; по решению руководителя места текстом, отдельных таблиц нет. Обновлены все семь артефактов. Current_location в batteries — предложенная техническая projection, не справочник. Открыты фактические идентификаторы, кадровый источник/права, отдельная регистрация и канонизация Q30. Следующий шаг — обсуждать API на этой модели, не возвращаться к прежним семи таблицам без нового требования.
