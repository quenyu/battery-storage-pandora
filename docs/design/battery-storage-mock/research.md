# Макет учёта АКБ: исследование и сценарии

29.09.2026. Актуальный объём: **демонстрационный макет**, а не внедрение на предприятии. Основание — исходное задание и последующие ответы пользователя. Существующий backend используется как прототип; новый Go-код сейчас не требуется.

Комплект: [требования](spec.md), [архитектура и API](architecture.md), [ER-модель](er-model.md), [DDL](schema.sql), [OpenAPI](openapi.yaml), [проверки](verification.md). Папка `battery-storage-pandora` описывает прежний прототип; его работающий контракт не подменяется этим проектным контрактом.

## Известное и принятые решения

- Одна ячейка вмещает строго одну АКБ — ответ пользователя.
- Объём: STORE, TAKE, RETURN, MOVE — ответ пользователя. LOST не включён.
- Сотрудник берёт только для себя и сам возвращает — ответ пользователя.
- Go, PostgreSQL, явный SQL/pgx, REST, Swagger; один backend, общий API для Web и ТСД — исходное задание.
- Для макета предлагается ручное создание сотрудников, условных идентификаторов и структуры хранения. Это техническое упрощение, не утверждение о Pandora.
- Оборудование имитируется запросами API. Управление замками, датчики, offline, интеграции и пользовательский Web-интерфейс не нужны для демонстрации БД/API.
- Credential — строковый условный код, не пароль. Фактический тип карточки и маркировки АКБ не устанавливается макетом.
- STORE одновременно регистрирует АКБ и помещает её в ячейку. Это выбранное упрощение макета.
- Автор STORE/MOVE — любой существующий активный сотрудник. TAKE и RETURN ограничены правилом самообслуживания на уровне данных команды.

## Назначение и участники

Система отвечает, где АКБ сейчас, у кого она находится, кто и когда её разместил, выдал, вернул или переместил. История сохраняется при замене кода сотрудника и отключении ячейки.

Участники: сотрудник — субъект учётной операции; демонстратор — создаёт справочники и выполняет запросы в Swagger; ТСД/Web — предполагаемые клиенты одного API. Раздельных пользовательских ролей и входа в макете нет. Указав чужой условный код, демонстратор может выполнить команду от его имени: проверка держателя является бизнес-правилом, а не доказательством личности.

Справочные данные: employees, employee_credentials, cabinets, shelves, cells. Транзакционные: создание АКБ и изменение её положения. История: battery_operations. Технические данные: idempotency_records. Системный аудит справочников — возможное расширение, не журнал движения АКБ.

## Сценарии

Общие правила команд: Idempotency-Key; проверка синтаксиса; разрешение действующего credential; атомарная запись состояния, события и результата. Успешный повтор проверяется до текущего состояния/отзыва карточки. Ошибки не оставляют изменений. Идентификаторы в примерах условные.

| ID | Сценарий и вход | Проверки | Изменения и событие | Результат и ошибки |
|---|---|---|---|---|
| UC-01 | Найти сотрудника: POST /credentials/resolve с value; отдельно создать: POST /employees с name/value | Непустая строка; при поиске активные карта и сотрудник; при создании уникальный код | Поиск без изменений; создание employee+credential одной транзакцией, без события АКБ | 200 employee_id/credential_id; создание 201; 404 неизвестный код; 409 занятый код. Не создавать человека автоматически при сканировании |
| UC-02 | STORE: inventory_code, employee_credential, destination_cell_id | Уникальная АКБ, действующий сотрудник, активные шкаф/полка/ячейка, свободная ячейка | Новая batteries STORED, версия 1; STORE с назначением | 201 операция+АКБ; 404; 409 INVENTORY_CODE_EXISTS/CELL_OCCUPIED/LOCATION_DISABLED |
| UC-03 | TAKE: battery_id, employee_credential | Под блокировкой АКБ состояние STORED; credential действующий | ISSUED; cell=NULL; holder=actor; version+1; TAKE с источником из БД | 201; 409 BATTERY_ALREADY_ISSUED; 404 АКБ/credential |
| UC-04 | RETURN: battery_id, employee_credential, destination_cell_id | ISSUED; actor=holder; целевое место активно и свободно | STORED, holder=NULL; RETURN с прежним держателем и назначением | 201; 409 INVALID_BATTERY_STATE/NOT_CURRENT_HOLDER/CELL_OCCUPIED/LOCATION_DISABLED |
| UC-05 | MOVE: battery_id, employee_credential, destination_cell_id, expected_source_cell_id | STORED; заблокированная ячейка АКБ равна ожидаемому источнику; другая активная свободная цель | Новая cell; MOVE с двумя местами; version+1 | 201; 409 SOURCE_MISMATCH/SAME_CELL/INVALID_BATTERY_STATE/CELL_OCCUPIED/LOCATION_DISABLED |
| UC-06 | GET /batteries/{id}: текущее состояние | UUID, существование | Нет изменений/события | 200 status, cell/holder, version, updated_at; 404 |
| UC-07 | GET /batteries/{id}/history | Существование АКБ, limit/offset | Нет изменений/события | 200 items по battery_version DESC; 404; 400 неверная страница |
| UC-08 | GET /cells/{id}/batteries | Ячейка существует, включая отключённую | Нет изменений/события | 200 items длиной 0..1; 404 |
| UC-09 | GET /employees/{id}/batteries | Сотрудник существует, включая отключённого | Нет изменений/события | 200 текущие выданные АКБ; возвраты остаются только в истории; 404 |
| UC-10 | Повтор после timeout: прежний ключ и тот же запрос | Хэш метода, пути и валидированного тела; результат прежней транзакции | При COMMIT повтор без изменений/события; после ROLLBACK выполняется заново | Прежний статус/тело; 409 IDEMPOTENCY_CONFLICT при другом запросе; 503 при временном отказе |
| UC-11 | Два TAKE: одна АКБ, разные сотрудники/ключи | FOR UPDATE одной строки; повторная проверка после ожидания | Один COMMIT и один TAKE; второй видит ISSUED | Один 201 и один 409; после отката первого второй может успешно выполниться |

Credential можно заменить атомарно, сохранив employee_id. Модель допускает несколько активных credential сотрудника; каждый код уникален за всю историю макета. Замена не переносит код на другого человека. Отзыв всех credential возможен, но до нового назначения сотрудник не сможет выполнить новую команду.

## Инварианты

INV-01: иерархия и уникальные номера внутри родителя. INV-02: код сотрудника не PK и не число. INV-03: АКБ либо в одной ячейке, либо у одного сотрудника. INV-04: в ячейке максимум одна АКБ. INV-05: TAKE только из STORED, RETURN только из ISSUED своим держателем, MOVE только из указанного текущего источника. INV-06: одно событие и изменение состояния одной транзакцией. INV-07: один успешный результат на ключ. INV-08: история не переписывается и не удаляется прикладным доступом.

## Что неизвестно, но не блокирует макет

Что именно за АКБ; реальные форматы меток; источник сотрудников; способ входа; физический шкаф; условия хранения; датчики; внутренние API; нормативы; объём нагрузки и сроки хранения. Эти сведения не имитируются утверждениями о компании.

Если понадобится именно внедрение, спросить наставника: откуда брать сотрудников/идентификаторы, как подтверждается физическая операция, кто имеет какие права, нужны ли партии/offline, как исправляются ошибки и проводится инвентаризация, какие измерения/нормы нужны, какие требования к резервному копированию. Сейчас это список возможного продолжения, а не анкета для завершения макета.
