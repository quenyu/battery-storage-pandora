# Промпт для запуска разработки

Скопировать блок в чат Codex, открытый в папке проекта, в режиме выполнения.

```text
$coding-orchestrator

Начни реализацию проекта battery-storage-pandora.

Рабочая папка:
C:\Users\Administrator\Desktop\pandora-golang

Стек: Go + PostgreSQL. Swagger UI обязателен.

Сначала изучи инструкции проекта и документы в docs/design/battery-storage-pandora/:
codex-task.md, spec.md, architecture.md, schema.sql, openapi.yaml, verification.md.

Это явное поручение перейти от проектирования к реализации. Указания в документах
«реализацию выполнять следующим этапом» теперь выполнены этим запросом.

Цель: работающий локальный backend с PostgreSQL, миграциями, REST API,
Swagger UI, тестами и понятной инструкцией запуска. Реализуй согласованный
объём v1 полностью, а не только каркас.

Основные правила:
- шкаф → полка → ячейка;
- одна ячейка вмещает максимум одну АКБ;
- сотрудник самостоятельно получает АКБ по штрихкоду;
- возврат возможен в любую свободную ячейку, в том числе другим сотрудником;
- поддерживаются размещение, выдача, возврат, перемещение, потеря и история;
- замена штрихкода сохраняет историю сотрудника;
- нужны атомарность, защита от двойной выдачи и обработка повторных запросов;
- без пользовательского frontend, SCADA, датчиков, уведомлений, администратора,
  ролей и системы входа. Swagger UI входит в объём как документация API.

Swagger:
- Go-сервис отдаёт Swagger UI по /swagger/, а /swagger перенаправляет туда;
- актуальный OpenAPI доступен по GET /openapi.yaml;
- единственный редактируемый источник контракта —
  docs/design/battery-storage-pandora/openapi.yaml;
- в UI доступны все маршруты, схемы, примеры, ошибки и Try it out,
  включая ручной ввод Idempotency-Key;
- запросы UI идут в /api того же сервера;
- UI, контракт и статические ресурсы поставляются с приложением и работают
  после запуска без интернета/CDN; внешний валидатор отключён;
- README содержит адрес Swagger UI, команды запуска и пример запроса;
- выполни браузерные проверки загрузки UI, создания и чтения сотрудника,
  повтора команды с тем же ключом и работы без внешней сети.

Начни с проверки окружения и минимального сквозного сценария через настоящую
PostgreSQL. Затем реализуй остальные сценарии. Независимые задачи делегируй
субагентам по правилам coding-orchestrator, сохраняя согласованность контрактов.

Обычные технические решения принимай самостоятельно, выбирая простые
поддерживаемые варианты. Не расширяй функциональность. Технические ошибки
проектных документов исправляй согласованно с кодом; существенные изменения
бизнес-правил уточняй.

Проверь сборку, миграции, API, Swagger UI и сценарии verification.md.
Конкурентность и транзакции проверяй на настоящей PostgreSQL, не только на mock.
OpenAPI и SQL ранее прошли статическую проверку; приложение, работающая БД
и Swagger UI ещё не проверялись исполнением.

Подготовь README, пример конфигурации без секретов и воспроизводимый способ
локального запуска. Не публикуй и не развёртывай проект во внешней среде.

Не останавливайся после составления плана. Доведи реализацию до проверенного
результата. В конце сообщи, что реализовано, как запустить и открыть Swagger UI,
какие проверки прошли и какие ограничения остались.
```
