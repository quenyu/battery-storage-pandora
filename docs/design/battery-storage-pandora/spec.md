# Система учёта АКБ — спецификация v1

Обновлено: 29.09.2026. Статус: реализован локальный Go backend с PostgreSQL и Swagger UI. Фактические проверки описаны в verification.md.

## Цель и границы

Учебный аналог реальной задачи Pandora для демонстрации навыков Go backend. Стек: **Go + PostgreSQL**. Реализация включает модель данных, миграции, REST API, OpenAPI, Swagger UI и автоматизированные проверки.

Связанные документы: [задание Codex](codex-task.md), [архитектура](architecture.md), [DDL](schema.sql), [OpenAPI](openapi.yaml), [проверки](verification.md), [исследование компании](company-research.md).

В объёме: сотрудники, их штрихкоды, шкафы, полки, ячейки, АКБ, операции и история. Физический шкаф и считыватель имитируются запросами API. **SCADA, условия хранения, датчики, уведомления, пользовательский frontend, администратор, роли, API-ключи и система входа исключены.**

**Swagger UI обязателен:** `/swagger/` с выполнением запросов через `Try it out`; актуальный контракт доступен по `/openapi.yaml`. Это документация разработчика, которая входит в объём проекта.

## Источники требований

На фотографии различимы шкаф, АКБ, люди, ШК/id, Go, PostgreSQL, API и задачи спроектировать БД и API учёта. Часть мелких подписей читается неуверенно; похожая на Swagger подпись использована как ориентир для OpenAPI. Позднее пользователь явно потребовал Swagger, поэтому интерактивный Swagger UI обязателен независимо от чтения фото. Упоминания frontend и условий хранения не расширяют объём после уточнений пользователя.

Подтверждено пользователем:

- ШК — **штрихкод**, хранится строкой.
- В шкафу произвольное количество полок; на полке произвольное количество ячеек.
- Одна ячейка вмещает максимум одну АКБ.
- Возврат разрешён в любую свободную ячейку.
- Сотрудник берёт АКБ самостоятельно.
- АКБ имеет собственную идентичность; её можно разместить, выдать, вернуть, переместить, отметить потерянной.
- Нужны API и PostgreSQL; настоящее оборудование подключать не требуется.
- Не нужно вводить администратора, роли и сложную авторизацию. Детальные ограничения на возврат и потерю пользователь делегировал выбору исполнителя.

## Принятые проектные упрощения

Это решения для демонстрации, а не утверждения о правилах предприятия:

- Сотрудник (user в исходном описании) представлен сущностью `Employee`: UUID, имя, дата создания. `Credential` отдельно хранит штрихкод и его жизненный цикл.
- У сотрудника один действующий штрихкод. Заменённый сохраняется, повторное назначение старого значения не предусмотрено. Ведущие нули значимы.
- Для учётной операции передаётся действующий `employee_barcode`. Это указание участника, а не проверка личности или авторизация.
- Любой сотрудник может вернуть чужую АКБ, переместить АКБ или отметить потерю. Автор и предыдущий держатель сохраняются отдельно.
- Регистрация АКБ сразу размещает её в ячейке. Состояния «создана, но нигде не находится» нет.
- Операция потери допустима из ячейки или у сотрудника. Потерянная АКБ сохраняется; обнаружение, списание и произвольные исправления — вне v1.
- Структуру хранения создают и читают. Удаление и перенумерация в v1 не предусмотрены.
- Вход по логину/паролю и API-ключи отсутствуют. Демонстрационный сервер по умолчанию слушает только `127.0.0.1`; штрихкод не считается секретом доступа.
- REST/JSON, OpenAPI 3.0.3; одно Go-приложение и одна PostgreSQL. Выбор HTTP-библиотеки не влияет на текущий контракт.

## Сценарии и требования

| ID | Сценарий | Результат |
|---|---|---|
| SC-01 | Создать сотрудника с именем и штрихкодом | Сотрудник и действующий идентификатор создаются атомарно |
| SC-02 | Создать шкаф, полки и ячейки | Адрес составляется из трёх номеров; количество потомков не фиксировано |
| SC-03 | Зарегистрировать АКБ | Устойчивые UUID и инвентарный код, занятая ячейка, операция register |
| SC-04 | Выдать АКБ по штрихкоду сотрудника | Статус issued, держатель — сотрудник, исходная ячейка свободна |
| SC-05 | Вернуть АКБ | Статус stored, выбранная свободная ячейка, предыдущий держатель в истории |
| SC-06 | Переместить АКБ | Новая ячейка и операция с исходным и целевым местом |
| SC-07 | Отметить потерю | Статус lost, текущее место неизвестно, последнее известное положение в операции loss |
| SC-08 | Найти состояние и историю | Поиск АКБ и фильтры истории по АКБ, сотруднику, ячейке и периоду |
| SC-09 | Заменить штрихкод | Старый недействителен для новых команд, история сотрудника сохранена |

`1.1.1` — адрес места, не идентификатор АКБ. Предъявление штрихкода без учётной команды не меняет состояние.

- **REQ-01:** одна АКБ занимает максимум одну ячейку; в ячейке максимум одна АКБ.
- **REQ-02:** состояние и история одной операции изменяются в одной транзакции.
- **REQ-03:** повтор успешной команды с тем же ключом возвращает прежний результат без второй операции.
- **REQ-04:** конкурентные конфликтующие команды не могут обе примениться к одному исходному состоянию.
- **REQ-05:** UUID сотрудника и АКБ сохраняют смысл истории независимо от замены штрихкода и перемещения.
- **REQ-06:** ошибки не оставляют частичных изменений; потеря не удаляет предмет или историю.
- **REQ-07:** Swagger UI запускается вместе с backend, отображает актуальный контракт и позволяет выполнять запросы с телом и Idempotency-Key. UI и контракт доступны локально без интернета.
- **REQ-08:** OpenAPI — единый источник контракта; HTTP-обработчики, UI и документация согласованы.
