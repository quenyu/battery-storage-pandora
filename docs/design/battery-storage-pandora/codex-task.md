# Задание для Codex: система учёта АКБ

## Цель и стек

Спроектировать API на Go и базу данных PostgreSQL для демонстрационного проекта, основанного на задаче предприятия Pandora. Проект предназначен для оценки навыков backend-разработчика.

Этап реализации запущен явным поручением пользователя 29.09.2026. Результат — локальный Go backend, PostgreSQL, миграции, REST API, встроенный Swagger UI и воспроизводимые проверки. Команды запуска находятся в [README](../../../README.md).

## Подтверждённые требования

- Структура хранения: **шкаф → полка → ячейка**. Количество полок и ячеек может различаться.
- В одной ячейке находится максимум одна АКБ.
- Каждая АКБ имеет собственный устойчивый идентификатор. Адрес `1.1.1` обозначает место хранения.
- Сотрудник самостоятельно получает АКБ. Возвращать можно в любую свободную ячейку.
- **ШК означает штрихкод.** Значение хранится строкой, включая ведущие нули.
- Сотрудник и карта/штрихкод различаются в модели; замена идентификатора не разрушает историю.
- Шкаф и считыватель имитируются запросами API.
- SCADA, условия хранения, датчики, уведомления и пользовательский frontend исключены. Swagger UI для документации API обязателен и входит в объём.
- Последующее уточнение пользователя: не вводить администратора, роли, API-ключи и систему входа; достаточно сотрудника с собственными полями. Возврат чужой АКБ разрешён как принятое упрощение, автор возврата и предыдущий держатель различаются в истории.

## Сценарии

1. Создать сотрудника и связать с ним идентификатор карты/штрихкода.
2. Создать шкаф, полки и ячейки.
3. Зарегистрировать АКБ и разместить в свободной ячейке.
4. Выдать АКБ сотруднику: определить его по предъявленному идентификатору, освободить ячейку, сохранить операцию.
5. Вернуть АКБ в любую свободную ячейку.
6. Переместить АКБ между ячейками.
7. Отметить АКБ потерянной, сохранив историю и последнее известное положение.
8. Просмотреть состояние и историю по АКБ, сотруднику, месту и периоду.

Предъявление карточки само по себе не создаёт выдачу: нужна отдельная команда API.

## Требования к проектированию

- Разделить текущее состояние и историю; учитывать тип операции, АКБ, участников, время и применимые места.
- Обновлять состояние и историю в одной транзакции.
- Не допускать двойную выдачу и размещение двух АКБ в одной ячейке.
- Определить обработку повторных команд без повторного применения.
- Не удалять историю при потере АКБ и замене карты.
- Разделить идентификацию сотрудника по карточке и авторизацию API-клиента.
- Предлагать простые технические решения с объяснением; допущения отмечать явно.
- Не расширять объём неподтверждёнными бизнес-функциями.

## Обязательный Swagger UI при реализации

- Вместе с Go-сервисом запустить Swagger UI по `/swagger/`, а `/swagger` перенаправлять на `/swagger/`. По умолчанию адрес — `http://127.0.0.1:8080/swagger/`.
- Отдавать актуальный контракт по `GET /openapi.yaml`. Единственный редактируемый источник — `docs/design/battery-storage-pandora/openapi.yaml`; не вести вторую ручную спецификацию.
- В UI доступны все маршруты, схемы, примеры, ошибки и `Try it out`, включая ввод обязательного `Idempotency-Key`. Запросы направляются в `/api` того же Go-сервера.
- Статические файлы Swagger UI поставлять с приложением; для работы после запуска интернет/CDN не требуется.
- В README указать адреса UI и контракта, шаги запуска и короткий пример запроса через UI. Проверить загрузку и выполнение запросов в браузере.

## Проверки реализации

Выдача → возврат в другую ячейку → перемещение должны сохранять согласованность состояния и истории. Занятая ячейка отклоняет вторую АКБ. Из двух конкурентных выдач успешна одна. Повтор команды не создаёт второй операции. Ошибка не оставляет частично применённых изменений. Потеря сохраняет последний известный след. Замена карточки не меняет принадлежность истории сотруднику.
